# ViewRed V1 — Handover Document

> **For the next agent**: this document describes the current state of the project, what's done, what's missing, and the rules you MUST follow. Read it end-to-end before doing anything.

## 1. Project in one paragraph

ViewRed is a **local network monitor** (bind `127.0.0.1:8080`, admin access via SSH tunnel) that captures packets, stores metadata in TimescaleDB, surfaces a React UI with real-time SSE, and uses local ML (Isolation Forest + Random Forest on ONNX) plus a local LLM (Qwen 2.5 3B via Ollama) for anomaly detection and a natural-language assistant. **Stack**: Go 1.26 (Gin + pgx/v5 + gopacket), React 18 + TypeScript + Tailwind, SSE for real-time, PostgreSQL + TimescaleDB, ONNX Runtime, Ollama. **Timeline**: 7–9 months solo / 3–5 with a 2–3 person team.

## 4. Toolchain and host constraints (READ THESE — they bite)

- **User is on Windows 11**. No Docker, no WSL, no `make`, no psql, no TimescaleDB locally, no Npcap. Available: Go 1.26.3, Node 24.16, npm 11.13, pnpm 9.12, Git 2.54, Ollama 0.30.9 with `qwen2.5:3b` loaded, winget, Chocolatey, Scoop.
- **CI is locked** to Go 1.25, Node 22, pnpm 9 (different from local).
- **`go test -race` does NOT work on Windows** (no CGO for race detector). Rely on idiomatic `sync.RWMutex` and CI for race testing.
- **gopacket/pcap CGo blocks Windows → Linux cross-compile**. This is an expected limitation; document when relevant.
- **Bind address**: `127.0.0.1:8080`. No secrets in repo (dev placeholders only).
- **For Windows smoke tests**: cleanup by **port** (`Get-NetTCPConnection -LocalPort 8080 | Stop-Process`), NOT by name. Orchestrator runs smoke tests inline; subagents only run unit tests.
- **`$env:GOOS = 'linux'`** doesn't work in PowerShell the usual way; use it as a per-command prefix or set the env var explicitly.

## 5. Hard rules (non-negotiable)

### TDD Iron Law
**NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST.** RED → GREEN → REFACTOR for every Go/TypeScript code task. The orchestrator is configured with `strict_tdd: true` (engram topic `sdd-init/viewred`); you MUST follow it.

### Commits
- **Conventional commits only**: `feat:`, `fix:`, `test:`, `chore:`, `docs:`, `refactor:`, `ci:`. Scope is allowed (e.g. `feat(api):`, `fix(web):`).
- **No AI attribution**. No `Co-Authored-By:` lines. No "Generated by" footers.
- **Work-unit commits**: one logical change per commit, even for size exceptions. For handler/test groups, use `feat(...): ... (size exception: NNN lines)` in the message.
- **Plan file edits** (`docs/superpowers/plans/...`) are committed separately as `docs(plan): mark Task N ...` to keep the work-unit clean.

### Code style
- **English only** in code, identifiers, function names, comments, UI copy, error messages. Spanish rioplatense only in conversation with the user.
- **Cross-platform**: works on Windows + Linux. Build tags where needed (none new in Plan 3).
- **No DI frameworks**. Constructor injection. Handlers take `Querier` interface; storage satisfies it; `ErrorQuerier` for 503 path.
- **Back-compat preserved**: existing constructors keep working; new ones are additive.
- **No `panic` in production code**. Return errors. Use `gin.Recovery()` for HTTP layer.

### SDD workflow (mandatory for new plans)
- **Preflight** before any SDD command: pace (interactive/auto), artifact store, PR strategy, review budget. Cache is in engram `sdd-init/viewred`. Re-ask only if the user changes scope.
- **Phases**: explore → propose → spec → design → tasks → apply → verify → archive. Each phase is a sub-agent. Apply is one sub-agent per task.
- **Whole-branch review** after a plan completes (fresh-context `sdd-verify`). Per-task reviews miss integration bugs; whole-branch review catches them. **Always do it.**
- **Size exceptions**: review budget is 400 lines; when a task exceeds, include `(size exception: NNN lines)` in the commit message and proceed (the user has pre-authorized this for handler groups).
- **Branch strategy**: Plan 2 used `feat/plan2-capture-and-storage` then fast-forward merged. **Plan 3 was committed directly to main** (user decision) — but Plan 4+ should consider using a feature branch again to keep main green while the plan is in progress. Ask the user.
